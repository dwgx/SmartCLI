# SmartCLI：可信终端交互运行时的大计划书

版本：本地执行计划 1.0 · 2026-09-15。目标：dwgx/SmartCLI。远端核查基线 `701e61f6d69aa2420617edf80b1136df8d5e8cf7`，树内0.2.3；本地开始时必须重新取HEAD。[N01]

这是设计与执行交接，不是已完成的SmartCLI升级。目录中的工具现在可用于本地导览、轻量验证和记录；产品源码改动由本地Agent实施。当前环境不能直接clone公共GitHub，也没有pyte，因此未宣称运行目标项目或竞品；本包工具自身的测试单独记录在evidence/。[证据边界]

## 1. 产品方向：可信交互，而不是更多shell按钮

服务的核心用户是写Agent/Harness的工程师，以及需要让Agent实际使用终端应用的人。目标工作流是持续会话里的感知、输入、等待、确认、恢复和结果验证；Vim、菜单、REPL、动态监视器、安装向导只是不同测试面。

保留现有Python默认生态、POSIX与ConPTY、库/CLI/MCP三入口、text/visual双hash、SS3模式、主备屏和设备查询响应。保留tui-ui/cmd-art，但将它们作为可控演示、布局测试和未来语义适配试点，不让装饰功能挤占运行时可靠性。现有资产详见项目导览和历史来源SC01–SC12。[N02]

三个阶段成果要分开：

| 层次 | 可交付成果 | 不能冒充什么 |
|---|---|---|
| 运行时可靠 | 字节不静默丢失，状态有界，错误可诊断，取消可收敛 | Agent一定懂应用 |
| 交互可验证 | 观察有版本，动作有进度，适配器可给ACK，独立结果断言 | 静默/画面变化一定是成功 |
| Agent实效 | 同模型、同任务、同预算下成功率/错误确认/成本的实测 | README功能表或主观分数 |

推荐对外定位：**让Agent在真实终端里行动，并能说明看到了什么、做到了哪一步、哪些结果仍不确定。** 这是建议定位，不是当前已满足的宣传承诺。

## 2. 本轮研究改变了哪些判断

Microsoft的`command_settled`在缺少追踪时也使用300ms静默回退；因此借鉴多类wait接口时，应把evidence_source和unknown显式化，不能仅改一个函数名。[N03]

xterm的write是异步解析；收到PTY输出、把数据交给parser、parser提交状态、生成图像是不同阶段。未来接入xterm/Ghostty等引擎时，需要明确解析屏障而不是只监听onData。[N05,N06]

ConPTY关闭可能产生最后一帧并需要排空通信通道。单一状态owner与平台I/O线程是兼容的；禁止让多线程修改pyte，不是禁止任何reader线程。[N07]

taria的bridge区分已连接状态、断线和从未收到快照，保留原语义tree与typed验证形式，并将ACK独立分发。SmartCLI可以借鉴“观察可容纳未知字段，执行必须严格验证”的分工。[N14]

MCP请求取消和可选Tasks的取消不是同一机制。先在内核设计cancel wait/interrupt/close三种动作，再做协议映射；2025-11-25规范的Tasks为experimental，不能要求全部Harness已支持。[N08,N09]

这些是源码/规范学习，不是已经跑过相同任务的竞品优劣证明。更细的修正见docs/02_RESEARCH_DELTA.md。

## 3. 固定的是验收不变量，开放的是实现路径

**必须保持：** 默认原生Windows路径；模型状态单owner；独立observer不互相吃事件；未确认失败不得谎报成功；资源预算有界；取消不默认杀整个shell；来源与推断分开；API迁移可回退；证据不泄露秘密。

**Agent可决定：** owner loop用线程+selector还是async actor；队列内部结构；分片处理修法；schema内部布局；默认日志编码；是否采用可选引擎；测试框架；模块拆分；迭代顺序。

**需要额外批准：** 公开API破坏性更改、默认引擎/许可证策略变化、远端发布、付费服务、公开上传日志、全局配置改动、重型真实PTY压力测试。既有“只有明确要求才commit”照旧。[N02]

自由发挥用ADR与X-实验任务表达。负结果也是成果：试验反驳某个设计，应记录后停止，不需要为了完成计划继续实现错误方案。

## 4. 第一轮：先理解，再完成一个真实改进

第一轮不是全量重写。Agent先交付PROJECT_MAP：当前HEAD和脏工作区、指令、解释器与依赖、入口链、状态所有权、测试入口、兼容面、已知未知。然后对A01–A06重审，从短写、SGR分片或CJK cell span中挑一个能安全验证的任务。

完成标准：原实现的负例有效；修复后同负例通过；控制组没有倒退；相关核心门禁跑过或明确NOT_RUN；vendor一致；工作区修改保留；没有未授权commit；可由另一个Agent复现。

T01/T02是理解与可证伪入口，不是必须花长时间写庞大报告的前置关卡。地图只需准确到足以支持当前修改；更深调用图随任务增量完善。

## 5. 里程碑与收口

| 里程碑 | 核心任务 | 允许进入下一阶段的证据 |
|---|---|---|
| R0 项目理解 | T01/T02/T45 | 当前源码地图、可执行测试清单、旧结论重新分类 |
| R1 输入与屏幕正确性 | T03/T04/T05/T06/T39 | 短写/分片/CJK负例和相关控制组；缺陷不被上层掩盖 |
| R2 有界会话运行时 | T07–T12/T47 | owner公平推进、有限队列、可取消watcher、关闭和退出状态 |
| R3 可信交互协议 | T13–T19/T42 | 完成证据等级、generation/seq/lease语义、明确降级、安全边界 |
| R4 观察效率与输入协议 | T20–T23/T40/T43 | region/diff等价与parse barrier；模式感知键鼠；成本实测 |
| R5 证据与人机共享 | T24–T27/T41/T48 | 精确状态截图、记录/重放限制、只读attach与受控接管 |
| R6 可选语义与远程 | T28–T30/T44/T50 | 明确适配范围、fallback、安全且可禁用 |
| 贯穿全程 | T31–T38/T46/T49 | 独立裁判、首次失败保留、源码/wheel/skills发行事实一致 |

这些不是固定发布日期。可以提前做独立测试工具、文档或ADR；不能为了跨阶段而把尚未验证的基础假设包装成完成。任务依赖图是初稿，本地Agent可以用证据重排。

首个可交付增量建议以R1收口：不绑定新UI、远程服务、语义树或全部键盘扩展。第二个增量以R2+必要R3协议为中心。R4以后根据用户真实任务与基准决定投入，避免再造一个无边界“全能终端平台”。

## 6. 建议架构：四条独立的状态轴

不要用一个ok字段覆盖全部过程。至少区分：

- 会话：created → running → closing → exited，未知退出应明确unknown。
- 输入：accepted → partially_written / written → app_acknowledged（仅支持者）→ verified（独立业务裁判）。
- 观察：received → parsed → committed observation；附session generation、revision、geometry/profile和loss状态。
- 等待：pending → satisfied / timed_out / cancelled / target_exited / predicate_error。

单一owner维护终端模型和原子状态切换；平台reader/writer只做I/O及有界队列。observer、日志writer、网络回包不阻塞owner。多个watcher检查同一revision，但不取得写权；writer lease用于控制实际输入。原子act减少竞态，却不提供TUI事务回滚。

最小实现可先不做完整actor框架。只要维持这些语义、通过故障注入，简单方案优先。不要为了实现一个命名架构大面积重写稳定代码。

## 7. 感知、能力与不确定性

屏幕文字、样式、光标和模式是观测事实；“这行是选中项”“红色代表报错”“这个状态栏表示成功”是推断。原生app接口提供的是应用声明，还需可信来源边界；即使有ACK也不等于最终业务结果正确。

逐步提供semantic_candidates、confidence/heuristic_reason、source、coverage、degraded_reason。允许没有selected，不要强选最大高亮段。UI角色和动作不能从ANSI中凭空变成真实DOM。

区分Unicode码点、grapheme cluster和终端cell。UAX29解决分段，不统一所有终端的列宽；CJK/emoji测试应记录Unicode版本和终端profile，而不是把某个模拟器选为无条件真理。[N12]

## 8. 资源和安全要成为产品契约

目标程序输出、MCP请求、慢观察者、日志磁盘和输入队列都可能无限增长。给每一层定义字节/条目/时间预算及溢出语义。canonical parser输入不能静默丢一段还声称画面准确；展示层可以合并快照，但必须让observer知道缺口。

超时必须覆盖单轮工作：外层deadline无法中断被卡住的同步regex、snapshot序列化或网络回包。优先literal/安全谓词，重型谓词移出owner并明确取消边界；不能只把一切包进不可杀线程。[N16]

PTY不是沙箱，MCP工具注释不是授权，session token不是与同权限子进程的完整隔离。shell标记、日志、语义tree和终端文字全部当不可信输入。真实隔离使用已有批准容器/VM/权限边界；本计划不自动部署任何沙箱产品。

单PTY与重型测试审批是本项目历史安全约束，不能因为性能研究而绕过。把高密度交错放到fake backend与虚拟时钟，真实会话只做串行确认。[N02,N04,N07]

## 9. 三条评测赛道

严格UI：只许屏幕、键鼠和wait，不许文件编辑绕过Vim。应用适配：可用声明过的Neovim/Textual/taria通道，单列适配成本。混合效率：可调用普通文件/API工具，衡量真实工作效率，但不宣称纯UI能力。

同一赛道固定模型版本、提示、可用工具、目标二进制版本、环境、预算、随机seed和独立裁判。记录任务成功、错误确认、输入丢失/重复、恢复、人类接管、CPU/RSS、工具轮次、token/截图成本。门禁级小样本与统计基准分开，不把一次通过当通用成功率。

零错误确认是设计方向与强验收要求；有限样本零错误不代表数学上永远不会错。性能阈值是本地基线校准后的预算，必须写出为何选择，不把本计划的初始建议当实测数据。

## 10. 允许Agent独立研究的议题

可选引擎有没有足够收益；区域稳定怎样避免spinner而不漏关键变化；可视高亮推断与原生语义如何融合；工具面应该组合成act-and-observe还是保持小原语；紧凑快照是否真的降低token且不降低正确率；自家tui-ui能否提供零猜测语义；失败轨迹能否自动缩减成可公开的无敏感fixture。

每个议题都要有假设、现状反例、替代方案、受限实验、停止规则和结果去向。不要求为了探索而实现所有方向。详见docs/07_AUTONOMY.md。

## 11. 交接与版本迁移

计划包不覆盖目标的AGENTS.md。state.json只是协调记录，evidence才是检查输入；机器可验证结构和hash，不能验证Agent是否诚实。已验证任务遇到源码变更需做影响复审，不能把旧日志静默当当前绿灯。

公共API优先加法兼容；若改变未知键处理、wait返回、hash/seq或者旧JSON字段，要加legacy测试与明确迁移。旧CRC是变化检测器，不是唯一身份、完整性证明或动作因果证据。

发布前分别验证源树、wheel、独立skill/vendor和MCP初始化。核心变更同步vendor；当前依赖和版本事实以代码/发行物为准。保留关闭自动Dependabot版本PR的用户决定；安全依赖审查可以人工或使用用户批准流程，不擅自重新打开机器人。

## 12. 怎么判断计划没有跑偏

每轮都能回答：解决了哪个真实失败？为何比最简单修法更值得？凭什么认定正确？哪些平台/边界没测？新增复杂度能否撤销？下一位Agent能否只读文件继续？

如果答案主要是“增加了多少模块、支持更多概念、README看起来更完整”，而没有原版负例和结果证据，应停下来缩小范围。**先让一次输入、一次观察和一次确认可信，再扩展到更多终端任务。**
